# Ideation — 2026-06-24

**Focus:** API + frontend value built on *data that already exists in the DB*. Scraper / enrichment
side is explicitly out of scope (assumed to be improving separately).

**Decisions taken into this run:**
- Scope: **genuinely multi-user** — ideas must treat onboarding, empty states, and per-user polish as first-class.
- Rich job fields (skills, salary range, days-in-office, experience level, company size): **assume they become real.** Build surfaces that exploit them.
- LLM appetite: **happy to spend more, but every LLM feature must let the user pick the model and default to a cheap one.**

---

## What this is

A **personal job-hunting command centre** (Go API in `cmd/api` + SolidStart frontend in `frontend/`).
It scrapes jobs, scores them **per-user** (cheap heuristic *Relevance* + LLM *Suitability* against a
user-authored rubric — `internal/score/`), tracks applications through **custom pipeline stages**
(`applications`, `application_statuses`), and surfaces your CVs **live as Google-Doc tabs**, exportable
to PDF (`tracked_docs` / `tracked_doc_tabs`, `cv-templates` routes).

**Who it's for:** job seekers who want a private, inspectable, self-owned alternative to Teal/Huntr —
now explicitly aimed at more than one user.

**Implicit thesis:** *be selective and intelligent.* Spend effort (scrape cost, LLM cost, the user's
attention) only where it pays off. Per-user scoring + a suitability gate already encode this bet.

## The unique asset (why this codebase can win)

Almost no competitor holds **all three** at once:
1. Your real, **scored job corpus** (`jobs` + per-user `job_scores`).
2. Your **actual CVs as structured, machine-readable Google-Doc tabs** — and *multiple variants per user*.
3. An **LLM already wired in** with a per-user **suitability rubric**.

That triangle — **jobs × CVs × LLM, per user** — is the moat. Teal/Huntr tailor *one* resume to a JD;
they never hold your variant library. Open-source trackers have the data ownership but no AI. This repo
sits in the empty quadrant.

## Competitive landscape (verified)

| Tool | Strength | Weakness we can exploit |
|---|---|---|
| **Teal** | JD-paired resume builder; live Match Score that "reflects gaps honestly" | Keyword-oriented matching; manual skill entry; builds resumes, doesn't hold *your* variants |
| **Huntr** | Full CRM tracking + semantic resume scoring; claims 2× interview rate from tailoring | Match score **overstates alignment** → false readiness; one resume, not a variant library |
| **Simplify** | AI autofill copilot + pipeline tracking | Autofill, not fit reasoning; no CV-corpus intelligence |
| **JobSync / ApplyKit / ApplyPilot** (OSS) | Self-hosted, data-private, BYO-LLM / Ollama | Single-applicant, single-resume; no aggregate "across my whole market" intelligence |

**Eureka 1 — the discarded explanation.** Open-source ATS roadmaps name the missing thing as *"visible
matching logic — why it scored that way."* This app **already computes** an LLM suitability score against
a rubric at ingest (`internal/score/`, called from `POST /ingest`) — then **throws the reasoning away** and
**won't even let the user edit the rubric** (`search_config.suitability_rubric` is stored, never surfaced).
The expensive work is done; the value is being deleted on the floor.

**Eureka 2 — variant selection beats variant generation.** Every incumbent *generates/edits one resume*.
This repo already stores **N CV variants per user** as tabs. The higher-value, structurally-exclusive move
is to **pick the best existing variant per job and show the gap** — no generation required for v1.

## Ideas

Tiered. Each lists the surface it touches and *why this codebase is uniquely positioned*. Tags:
`[today]` works on currently-stored data · `[enrich]` relies on the incoming structured fields.

### Adjacent

#### 1. Glass-box scoring — capture the suitability *reasoning* + edit the rubric & thresholds  `[today]`  ⭐ Eureka 1
**Surface:** `internal/score/`, `job_scores`, `POST /ingest`, `/jobs` table, `/jobs/{id}`, `settings/searches`.
The suitability LLM call already runs. Extend its output schema to also return **matched signals, missing
signals, and a one-line rationale**; persist them (new nullable columns on `job_scores` — `reasoning`,
`matched`, `missing`). Surface as an expander on the job row and a panel on job detail ("Suitability 82 —
*strong: Go, distributed systems · missing: Kafka, on-call*"). **And finish the 60%-there config surface:**
`suitability_rubric`, `relevance_cutoff`, `notify_threshold` are all stored but **uneditable** — give them
a real settings form. Multi-user note: ship an empty-state that explains the rubric and offers a starter
template so a new user's scores aren't silent.
**Why uniquely positioned:** the costly call exists; this is *reuse, not new spend.* Directly answers the
incumbents' opaque-score weakness. **Lift:** small. **Risk:** prompt-schema change must stay backward-safe on re-score.

#### 2. AI settings — per-user model picker, default-cheap  `[today]`
**Surface:** new `settings/ai` page + a `user_ai_prefs` row (or columns on `search_config`); read in `internal/score` and any future LLM caller.
A single place to choose the model used for suitability + every LLM feature below, defaulting to a cheap
model. Directly from the stated requirement; also the **enabler** that makes ideas 1, 4, 5, 8 safe to ship
multi-user (each user pays their own way / picks their tier).
**Why uniquely positioned:** scoring already centralises LLM access in one module — one seam to plumb a model arg through. **Lift:** small. **Risk:** low. Flagged `scope risk: low` — orthogonal to the thesis but a hard dependency of the LLM ideas, so it earns its place.

#### 3. Score-validated funnel analytics — does the score predict responses?  `[today]`
**Surface:** `/insights` (charts infra already exists), joins `job_scores` × `applications` × `application_statuses` × `jobs.source`.
The insights page already charts discovery/pipeline. Add the loop-closing question: **"jobs I scored >80
and applied to → 30% reached a response vs 8% baseline."** Break conversion down by score band and by source.
This both delights ("my scoring actually works") and tells the user where to spend effort.
**Why uniquely positioned:** every table needed is already per-user and already joined elsewhere; no incumbent
has your scores *and* your real outcomes. **Lift:** small–medium. **Risk:** thin data for a brand-new user → needs an honest empty-state.

### Expansion

#### 4. Best-CV-for-this-job — variant ranking + gap analysis  `[enrich]` + `[today]`  ⭐ Eureka 2
**Surface:** `/jobs/{id}`, `cv-templates` pipeline (`tracked_doc_tabs`, PDF/Docs export already wired), `internal/score`-adjacent matcher.
For a given job, **rank the user's CV variants by fit** and show the **gap** (skills/requirements in the JD
absent from the chosen CV): *"Best CV: 'Platform-eng variant' — 84% · missing: Terraform, gRPC."* v1 needs
CV **text** — you already pull tabs and export them, so extract text from the same path. Uses the model from
Idea 2.
**Why uniquely positioned:** you hold **multiple CV variants per user** as structured tabs — the one thing
Teal/Huntr can't touch. **Lift:** medium. **Risk:** CV text extraction quality; cache per (tab, job) to control cost.

#### 5. Tailored application draft — cover letter / bullet suggestions from JD × chosen CV  `[today]`
**Surface:** `/jobs/{id}` → `applications` (store on `applications.notes` or a new `draft` column), uses Idea 4's chosen variant + Idea 2's model.
Given the full job description (already stored) and the selected CV variant, generate a **draft cover letter**
and **tailoring suggestions**, saved against the application so it travels with the pipeline card.
**Why uniquely positioned:** full descriptions are stored, CV tabs are accessible, and `applications` already
links job↔user. This is the "2× interview rate" feature incumbents charge for — built on data you own.
**Lift:** medium. **Risk:** generation quality / hallucinated claims → constrain prompt to CV-grounded facts only.

#### 6. Market skills-gap radar — portfolio-level, not per-application  `[enrich]`
**Surface:** `/insights`, aggregates the structured `skills` field across the user's *relevant* job corpus vs skills present in their CV tabs.
*"Appears in 61% of jobs you score >70, absent from all your CVs: Kubernetes, Terraform, Go."* No
per-application tool gives this — it requires the **whole scored corpus + your CV library** at once, which is
exactly what this repo has.
**Why uniquely positioned:** aggregate intelligence over the corpus is impossible for a browser-extension
incumbent that only sees one JD at a time. **Lift:** medium. **Risk:** depends on the incoming structured `skills` field — `scope risk: low`, but gated on enrichment landing.

#### 7. Salary intelligence — normalise `salary_raw`, benchmark your offers  `[today]` → `[enrich]`
**Surface:** `/insights` + `/jobs` filters; parses `jobs.salary_raw` (stored raw by design — ADR-0007) and `applications.salary_info`.
Parse raw salary into normalised ranges and chart the comp distribution across your relevant jobs; benchmark
the offers/figures you log on applications against the live market you're actually seeing.
**Why uniquely positioned:** ADR-0007 deliberately preserves raw salary precisely so a parse layer can be
added later **without re-scraping** — this is cashing that decision in. **Lift:** medium. **Risk:** messy free-text salary parsing; start heuristic, escalate to the cheap LLM only on misses.

### Moonshot

#### 8. Application Copilot — turn the passive tracker into an active daily loop  `[today]` + `[enrich]`
**Surface:** cross-cutting — `job_scores`, `tracked_doc_tabs`, `applications`, `application_statuses`, the existing `notification_digests` / email digest, a new `/apply` queue page.
Wire the isolated pieces into **one loop**: each day, surface the top-suitability un-actioned jobs → for each,
**pre-select the best CV** (Idea 4) + **draft the cover letter** (Idea 5) + **one click to create the
application in a "Drafted" status** (Idea 1's reasoning shown inline as justification). The digest email
already pushes high-suitability jobs — this makes that push **actionable** instead of informational.
**Why uniquely positioned:** every component already exists in isolation and is already per-user; the moonshot
is the *orchestration*, not new primitives. This is the product's thesis ("be selective") expressed as a
workflow rather than a filter. **Lift:** large (composes ideas 1, 4, 5). **Risk:** only worth building once
1/4/5 exist — it's the capstone, not the start.

## Recommended build order

**Start with Idea 1 (Glass-box scoring) as the tracer bullet.** It is the cheapest (reuses an LLM call you
already pay for), the most immediately visible, it directly attacks the incumbents' headline weakness
(opaque/over-optimistic scores), and it produces the **rubric + reasoning substrate** that Ideas 4, 5, and 8
all consume. Ship Idea 2 (model picker) alongside it so the reasoning capture is multi-user-safe from day one.

**Tracer-bullet first slice (Idea 1):**
1. Add `reasoning` (text), `matched` (text[]), `missing` (text[]) nullable columns to `job_scores` (migration in `scripts/migrations/`).
2. Extend the suitability prompt's output schema in `internal/score/` to return those three; persist on ingest. Keep it backward-safe (null when scorer not configured).
3. `GET /jobs` and the job detail handler return the new fields; render an expander on the `/jobs` row and a panel on `/jobs/{id}` — with a proper empty-state for unscored jobs.
4. Add the `settings/searches` form to edit `suitability_rubric`, `relevance_cutoff`, `notify_threshold`, with a starter-rubric template for new users.

**Then:** Idea 4 (best-CV matching) as the flagship differentiator → Idea 5 (drafts) → Idea 8 (copilot) as the capstone. Ideas 3, 6, 7 are independent insights wins that can slot in anytime.

**Next step:** take Idea 1 into `write-a-prd` to lock scope and the `job_scores` schema change before building.
